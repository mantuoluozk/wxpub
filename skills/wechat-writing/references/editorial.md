# 成稿与编辑

## 起草

- 写前用一两句确定读者、读者要解决的问题，以及全文最值得说的判断。长篇需要梳理论证时，参考 `upstream/wewrite/wewrite-write/references/article-brief.md`；按题材选结构。
- 第一段直接交代判断、具体发现或操作结果。每一段增加证据、步骤、限制或判断。重复的段合并，能用一句讲清的直接写一句。
- 按证据决定篇幅。优先使用具体事实、必要的例子和可复制的命令；表格只用于能对齐口径的对比。FAQ、金句、总结、引导互动和固定节数按稿件需要选用。
- 有作者样文时，参考一两篇同类文章的开头、句长、断句和收尾。需要从作者已有记录补证据时，按 [个人素材与调研](research.md) 搜索。经历和第一手观察只用作者实际提供的材料。素材撑不起某个判断时，缩小范围或注明边界。
- 版本号、实测数据、引用、比较条件与原文核对。来源或条件明确写出来，区分事实、推断和作者判断。已有事实核查文件时按项目约定更新。

## 三遍审校

1. **内容。** 从头读一遍，核对事实、论证顺序和证据边界。看开头有没有把问题说清，每一节是否支撑核心判断。偏题、漏说必要前提或引用口径变了，先修这些。
2. **表达。** 读取 `upstream/humanizer-zh/SKILL.md`。优先处理六类问题：空泛铺垫或结尾、反复套同一句式、绕弯的书面表达、硬拆小标题和列表、含糊到没有判断的段落、缺少证据的抽象评价。删复读段，能在一小段讲完的就写成一小段。材料有实测时写具体，没有就保留事实边界。保留数字、代码、链接、归因及不确定性。
3. **节奏。** 按手机阅读顺序通读，拆开读着卡的长句，合并刻意切碎的段落，删掉读者刚看过的总结。保留 Markdown 和 YAML 结构，需要回看出处的地方核对后再定稿。

审稿顺序参考花叔的 [三遍审校](https://github.com/alchaincyf/huashu-skills/tree/master/huashu-proofreading)，具体句式和语气以作者样文和 Humanizer-zh 为准。


## 修改已有稿件

用户指定了修改范围时，直接改对应内容。结构重排或跨多章节改稿时，先列出实际要动的几处，按相关段落分批保存。只有用户要求先看修改方案，或会变动用户原本的观点且范围不清时，再确认范围。用 diff 核对改动，保留用户在文件里已有的其他改动；交付时简要交代结构、事实或引用有哪些实质变化。方法参考花叔的 [文章编辑](https://github.com/alchaincyf/huashu-skills/tree/master/huashu-article-edit)。

## 学习作者文风

当前稿直接从用户给的样文学习。需要下次继续复用时，才使用 WeWrite 本地范文库，安装命令为 `uv tool install wewrite`。用户明确标为本人文章时，用 `wewrite exemplar <成稿路径> --user-authored`，用 `wewrite exemplar --list` 查看。后续起草时运行 `wewrite home` 定位状态目录，从其中的 `exemplars/index.yaml` 找到与本次稿件同类的本人范文，最多读两篇；状态目录不存在或没有匹配样文时，直接用当前材料起草。学习现有 WeWrite 任务的人工改稿时，读 `upstream/wewrite/wewrite-learn/references/learn-edits.md`；没有任务时，可先对读用户提供的前后两稿，由作者确认哪些改法值得沿用。范文和作者稿放在本机，成稿只采用与当前体裁相关的偏好。
